## 区块包回归修复（level_chunk_with_light 0x2C）

用户报告：主世界与下界双双进不去，客户端直接断开（disconnect 日志 2026-08-09）。

根因：上一轮「修复」把 `ChunkEncoder.writeChunkPacket` 的光照写入从 `writeByteArray` 改成 `writeRawBytes`，
**漏掉了每个 2048 字节光照数组前的 `VarInt(2048)` 长度前缀**。真值来自 `mapping/deobf-work/remapped_server_1.21.11.jar` 反编译：
`ByteBufCodecs.byteArray(2048)` 的 decode=`FriendlyByteBuf.readByteArray(buf,2048)`=先 `VarInt.read()` 再按长度读字节；
encode=`writeByteArray`=先写 `VarInt(2048)` 再写 2048 字节。

后果：
- 主世界天空光填 0xFF → 客户端把首个 0xFF 当 VarInt 续位位连读 5+ 字节 → `VarInt too big` 崩溃。
- 下界/末地天空光填 0x00 → 客户端把 0x00 当下标 0，吞掉全部 16×2048 光照数据，剩余 32752 字节（desync，不报错但光照全丢）。

验证方法（权威）：`tools_test/VerifyWithVanilla.java` 用真实 vanilla `ClientboundLevelChunkWithLightPacket.STREAM_CODEC.decode`
断言 `readableBytes()==0`。修复后主世界/下界/末地各 5 个坐标共 15/15 PASS（包长 49974 / 33525）。

附带修正：heightmap map 的 key 由错误的 0/2 改为 `Heightmap.Types` 的 id（WORLD_SURFACE=1, MOTION_BLOCKING=4）。

教训：自编自解「外层 0 剩余」会复用同样的错误假设 → 假阳。必须以真实客户端解码器做 oracle。

下一步（尚未做）：继续 Request B part 1（传送卡加载界面）与 part 2（生存模式功能审计 P1-P8）。

## 传送/重生卡「加载地形中」界面（Request B part 1）已修复

用户报告：下界能生成（624 个区块已发，0x0B 也已发），但客户端的「加载地形中」界面不关闭，必须重进服务器。

根因（查证 authoritative，非猜测）：
- 1.21 起客户端离开加载界面必须满足：收到 **Game Event 13 (LEVEL_CHUNKS_LOAD_START)** **且** 玩家处于已加载/已编译的区块。
  来源：Minecraft Wiki Protocol FAQ + DeepWiki mc-1.21.4「Loading Screens and Level Loading」。
  `LevelLoadStatusManager` 状态机：WAITING_FOR_SERVER → WAITING_FOR_PLAYER_CHUNK(区块编译) → LEVEL_READY(关界面)。
- 登录流程 `sendLoginPlay` 末尾已发 `0x26`(game_event) `writeByte(13)+writeFloat(0.0f)`（见 NetworkHandler 5880）→ 所以登录正常。
- 传送/重生路径（`teleportToDimension` 与死亡 Client Command action 0）**只发了 0x50 重生 + 0x46 传位 + 区块**，**从没发 Game Event 13**。
  原版在 `PlayerList.sendLevelInfo`(PlayerList.java:583) 对死亡重生与维度切换都发 `LEVEL_CHUNKS_LOAD_START`；我们只发了区块，导致客户端 `LevelLoadStatusManager` 停在 WAITING_FOR_SERVER，界面永不关闭。
- 0x0B (ChunkBatchFinished) 经反编译确认**只更新自适应批量统计**，**不关闭界面**（hig.a(ado)→hhx.a(int)，纯数学），所以「确保发 0x0B」方向错误。

修复（NetworkHandler.java）：在 `teleportToDimension`（4141 行）与死亡重生 handler（330 行），0x46 传位之后、`sendInitialChunks` 之前，各加：
```java
sendPacket(ctx, 0x26, pb -> { pb.writeByte(13); pb.writeFloat(0.0f); }); // Game Event 13 = LEVEL_CHUNKS_LOAD_START
sendPacket(ctx, 0x6F, pb -> { pb.writeLong(0); pb.writeLong(6000); pb.writeBoolean(true); }); // SetTime
```
0x26 的 1.21.11 包号已用 xKumorio 表核对（1.21.9–1.21.11 = 0x26），格式照 `ClientboundGameEventPacket.write`（`writeByte(event.id)+writeFloat(param)`）。
注意：曾误加 0x39(ChangeDifficulty)/0x38(PlayerAbilities)，但其 1.21.11 包号未核实（xKumorio 表只到 1.21.6=0x27），错包会破坏客户端解码流，已删除，仅保留已验证的 0x26+0x6F。

编译：`javac @javac_args.txt` 通过（仅既有警告）。
