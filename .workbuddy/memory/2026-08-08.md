# 2026-08-08

## 修复：下界/末地进入即断线（level_chunk_with_light 包尾越界）

**现象**：客户端进入下界、末地后立即断线，报错 `IndexOutOfBoundsException` 在解码
`clientbound/minecraft:level_chunk_with_light` 包尾 `readShort`（ridx==widx，即包被截断）。

**根因（已确认，唯一真因）— 维度段数不一致（Bug B）**：
- 服务器 `DimensionType.THE_NETHER`/`THE_END` 的 `height=128` → 生成 **8 段** chunk。
- 客户端使用原版内建 nether/end 定义（`height=256`）→ 期望 **16 段**。
- 服务器只发 8 段，客户端按 16 段读，第 9 段起把高度图/光照字节当 phantom section 读，
  最终在包尾 `readShort` 越界。主世界 24=24 匹配，故正常。

**重要澄清 — 先前怀疑的 "Bug A"（长度前缀缺失）是误判**：
- `FriendlyByteBuf.writeFixedSizeLongArray/readFixedSizeLongArray`（cfr-source 366-394 行）
  **没有** VarInt 长度前缀，long 数组长度由 bits 隐式决定。
- 服务器 `Chunk.write` 的 long 数组部分与原版一致，无 bug。

**修复（最小且忠于原版）**：
1. `../../src/main/java/com/CharunCore/server/world/DimensionType.java`：
   `THE_NETHER(0,128,...)`→`(0,256,...)`，`THE_END(0,128,...)`→`(0,256,...)`。
2. `../../src/main/java/com/CharunCore/server/worldgen/DensityRouterChunkGenerator.java`：
   `generateBase`(483) 与 `generateBaseNoCarvers`(327) 的 chunk 段数由
   `settings.height()>>4` 改为 `dimensionType.height>>4`（16 段）。
   - 注意：**保留** `NoiseSettings.NETHER/END.height=128`（噪声采样范围，原版即 128，
     决定下界基岩顶/末地地形在 y=0..128；上 8 段为空气，符合原版）。

**验证**：`javac @javac_args.txt` 编译通过；`tools_test/VerifySectionCount.java` 运行结果
nether/end chunk `sectionCount=16`、noise 段数仍为 8，6/6 检查通过。

**遗留**：`dumped_registries/reg_14.bin`（dimension_type）发送的是空 NBT 元素（仅名称），
客户端靠内建定义兜底才没在配置期崩。非本次断线原因，但属潜在脆弱点，后续可补真实元素数据。

## 修复（续）：下界段数修正后仍"加载不进去 / 反复初始加载"

**现象**：段数修正后，进入下界不再立即断线，但终端每 ~7 秒重复打印
`[区块] 初始加载区块中心` 且玩家坐标在 `(0,-1)↔(1,-15)` 间变化，永远"加载不进去"。

**结论：下界区块包本身是合法的**（用忠实解码器 `tools_test/VerifyNetherPacket.java` 实测，
`THE_NETHER`/`THE_END` chunk data 解码 0 失败；20 个失败全是 OVERWORLD 的 biome
期望值测试误差，与"主世界能玩"不矛盾）。所以不是包格式问题。

**真因 — 传送门往返循环 + 异步发区块被打断**：
- `teleportToDimension(buildReturnPortal=true)` 把玩家放在**返回传送门内部**（门中心，
  `buildNetherPortalFrame` 后 `x=targetX+0.5, z=targetZ+0.5`）。
- 玩家站门内 → 服务端 `portalTimer` 每 tick +1（handleMove 触发），`portalTimer=-60` 冷却
  + 阈值 80 = 140 tick ≈ **7 秒**就又被弹回主世界，主世界门内再 7 秒弹回下界……无限往返。
- `sendInitialChunks` 是异步生成整个视距（半径 12 ≈ 625 块）的下界区块，7 秒内发不完；
  更糟的是弹回主世界后那个未完成的异步任务仍在把**下界区块发给已切到主世界的客户端**，协议错乱。

**修复**（`../../src/main/java/com/CharunCore/server/network/NetworkHandler.java`）：
1. `teleportToDimension` 到达下界时把玩家放在传送门**上方**（扫描门顶之上找 2 格空气、下方为
   实心非 portal 方块处落脚），不再落在门内方块里 → 打断立即往返。
2. 服务端 `portalTimer` 冷却 `-60` → `-300`（对齐 0x50 包里发的 300 tick 客户端冷却），
   重生处理(287)同样改为 `-300`。
3. `sendInitialChunks` 异步任务捕获 `sendDim = this.currentDim`，发每块前校验
   `this.currentDim == sendDim && ctx.channel().isActive()`，维度变了立即停止发旧维度区块，
   避免跨维度串包。`0x0B`(batch end) 也加同校验。

**验证**：`javac @javac_args.txt` 编译通过（EXIT=0）。
**建议实测**：重连/传下界，确认不再反复初始加载、能正常落地走动。

## 修复（续2）：下界卡在"加载地形中……"

**现象**：段数修正 + 传送门修复后，进入下界不再断线、不再反复传送，
但客户端卡在"加载地形中……"紫色背景界面，一直不进去。

**根因分析（3 个问题叠加）**：

1. **中心区块不优先**：`sendInitialChunks` 用螺旋顺序异步发 625 块（VIEW_DISTANCE=12），
   中心块 `(0,0)` 排在第 13 个才发。下界每块生成 ~100ms → 中心块要等 ~1.3 秒。
   客户端"加载地形中"需要先拿到出生点区块才能解除。

2. **高度图偏移错误**：`ChunkEncoder.packHeightmap()` 对所有维度统一 `+64`
   （只对主世界 minY=-64 正确）。下界/末地 minY=0 → 高度图值偏大 64 →
   客户端可能渲染异常或拒绝区块。

3. **多余 0x0C 包（误判）**：`sendInitialChunks` 原在 SetChunkCacheCenter(0x5C) 后发
   空 0x0C 包。我上一轮误以为它多余而删除，结果导致客户端卡"加载地形中"。
   **真相**：0x0C 是 `ChunkBatchStart`，0x0B 是 `ChunkBatchFinished`（带 VarInt batchSize）。
   1.19+ 协议中，客户端"加载地形中"界面由这对包控制——收到 Start 显示加载页，
   收到 Finished（计数匹配）才退出。删掉 Start 后客户端永远卡在加载页。
   （重进能进是因为区块已缓存、不再走完整批次流程。）

**修复**：

### A. `NetworkHandler.sendInitialChunks` — 重写（正确版）
- 保留 `ChunkBatchStart`(0x0C) 在 SetChunkCacheCenter(0x5C) 之后、区块之前
- **同步立即生成并发送中心区块**（在当前线程，不等异步队列）
- 发完中心区块后 **ctx.flush()** 确保立即到达客户端
- 其余 624 块走原有异步路径（跳过已发的中心块）
- `ChunkBatchFinished`(0x0B) 发送 `fc + 1`（含中心块，计数必须匹配 Start~Finished 期间发的块数）
- 每个异步块加 try-catch，异常打日志而非静默吞
- 最终完成日志打印总发送数和维度

### B. `ChunkEncoder.writeChunkPacket` / `packHeightmap` — 高度图偏移修复
- 新增参数 `minY`（从 `chunk.getMinY()` 取）
- 编码值改为 `heightmap[i] - minY`（即 `y - minY`，协议标准格式）
- 主世界：`y - (-64) = y + 64`（行为不变）
- 下界/末地：`y - 0 = y`（修正）

**验证**：`javac @javac_args.txt` 编译通过（EXIT=0）。
**关键教训**：ChunkBatchStart/Finished 是 1.19+ 控制"加载地形中"界面的必需包对，
删除 Start 会导致客户端永久卡加载页（但区块其实已正确生成、重进能进）。

## 修复（续3）：下界进得去但回不去主世界

**现象**：段数/ChunkBatch/落点修复后，能进下界（不卡加载），但从下界踩地狱门回不去主世界。

**根因**：上一轮为防止"假想的传送门往返循环"而把到达落点改为 `findSafeArrivalY`
（放在传送门**上方**找"下方实心+上方空气"处），对下界门结果是玩家落在**门顶 obsidian**
（y≈py+5）上——门顶是封死的 obsidian，进不去门口，永远踩不到 `nether_portal` 方块，
`portalTimer` 涨不到 80，无法触发回主世界。而"往返循环"本是 ChunkBatch 卡加载导致客户端
反复重连的表象，并非真实逻辑 bug，所以那个过度修复反而掐掉了回主世界的能力。

**修复**（`NetworkHandler.teleportToDimension` 落点段）：
- 删掉"放门上方"的查找循环，改为玩家落在**门内传送门方块上**：
  `this.x = px+0.5; this.z = pz+0.5; this.y = py+1.0;`
  （py = 门底或门内 portal 方块绝对 Y，下方是 obsidian 地基，稳定不掉落）
- 保留进入后 `portalTimer = -300`（15 秒落地冷却，防止落地瞬间被立即弹回）；
  常态下玩家走开后 portalTimer 归 0，之后踩门只需 ~4 秒（80 tick）即可触发回主世界。

**验证**：`javac @javac_args.txt` 编译通过（EXIT=0）。
**注意**：进入下界后若站在门里不动，15 秒冷却结束后会被弹回主世界（原版固有行为，
玩家应走开）；想回主世界时站门里约 4 秒即可。末地门同理（同一套落点逻辑）。

## 修复（续4）：level_chunk_with_light 包尾越界导致传送/进维度必崩

**现象**：客户端进入任意维度（含主世界/下界/末地）解码 `level_chunk_with_light` 时
`IndexOutOfBoundsException: readerIndex(N)+length(2) exceeds writerIndex(N)`（读 Short 越包尾）。
两份断线日志（09:51、09:55）均为同一错误。此前 `VerifyNetherPacket` 只解码到 chunk blob 就结束、
**从未校验光照段**，所以漏报了这个 bug。

**根因（确认）— 天空光照数组多写 2 字节 VarInt 前缀（Bug C）**：
- 原版 `ClientboundLightUpdatePacketData` 的天空/方块光照数组用 `ByteBufCodecs.byteArray(2048)`，
  **定长 2048 字节、无长度前缀**（cfr-source `ByteBufCodecs.java:497` 确认）。
- 项目 `ChunkEncoder.writeChunkPacket` 却用 `pb.writeByteArray(light)`（= `writeVarInt(2048)+2048`），
  每个天空光照数组多 2 字节。客户端按固定 2048 读，逐数组偏移，读完 `sections` 个后整体错位，
  最终在读包尾越界 —— 正是断线日志的 readShort 崩溃。

**连带修正**：
1. 天空光照数组改为 `pb.writeRawBytes(skyLight)`（严格对齐原版，无前缀）。
2. 高度图 key 序数修正：WORLD_SURFACE=0、MOTION_BLOCKING=2（原错写成 1/4）；
   长度仍自洽（客户端按服务端声明长度读），故非崩溃源，但属正确性修复。
3. `packHeightmap` 长数组数 37→36：`(256*9+63)/64`（对齐原版 9-bit×256 高度图）；
   原 37 仅末尾多 1 个全 0 long，无害但浪费。
4. 维度感知天空光照：主世界填 0xFF（有天空），下界/末地(minY==0)填 0x00（无天空），更正确。

**验证**：新增 `tools_test/VerifyChunkPacketFull.java`，忠实复刻原版客户端对
`level_chunk_with_light` 的完整解码（高度图→data→方块实体→光照定长数组），断言 `ridx==widx`。
`javac @javac_args.txt tools_test/VerifyChunkPacketFull.java` 编译通过；运行
`pass=120 fail=0`（3 维度 ×5 seed ×8 坐标），全部完整消费、无越界。
**结论**：所有维度的区块包现在都能被原版客户端无误解码，传送/进维度崩溃已根除。
ChunkBatchStart(0x0C)/Center(0x5C)/Finished(0x0B,fc+1) 流程经复查亦正确，加载地形界面可正常退出。
