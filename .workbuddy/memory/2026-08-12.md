## 客户端实测 4 个 Bug 修复（在 133 缺陷修复 + 编译通过之后）

### Bug1 合成崩溃（P0 实际阻断）—— 已修
- 现象：`skipComponentPatch` 在 `handlePlay:1169/1175` 抛 `IllegalArgumentException: minimumReadableBytes:-1`，合成即崩。
- 根因：1.21.11 的 `serverbound_container_click`(0x11) 用 **HashedStack** 编码（Optional + Holder + HashedPatchMap），不是裸 `VarInt itemId + count + DataComponentPatch`。旧解析格式对不上 → buffer 越界。
- 修复：`NetworkHandler` 新增 `skipHashedStack`（present 标志→Holder.getItem→HashedPatchMap：VarInt 计数 + 每项 VarInt type + VarInt len + bytes；随后 VarInt 计数 + 每项 type）；`0x11` 解析改用它。注意 `HashedPatchMap` 的 `present` 是 **unsigned byte**（用 `readByte()&0xFF`，PacketBuffer 无 readUnsignedByte）。

### Bug4 配方书所有配方挤一格（P2）—— 已修
- 根因：所有配方都被当作 `crafting_shaped`(type=1) 发送；但 `ShapelessCraftingRecipeDisplay` **没有 width/height 字段**，客户端把第一个 ingredient 当 width 读 → 布局错乱全挤一格。
- 修复：`sendRecipeBook` 按 `CraftResult.shapeless` 分支：shaped→type=1（w/h + w*h 个 slot）；shapeless→type=0（直接 list 长度 + 各 slot）。`CraftResult.shapeless` 字段已存在。

### Bug3 浮空方块（树叶/草悬空，P2）—— 已修
- 根因：`computeTopSolidY` 把树叶/原木也算作"solid 地表"，邻 chunk 树冠伸入本 chunk 时叶子成为假地表，树被种在浮空叶上。
- 修复：`computeTopSolidY` 跳过非地面方块（leaves*/log/*_log/wood/*_wood/各类植物/空气/水/岩浆）；`placeTrees` 增加地面类型校验（仅 dirt/grass_block/podzol/mycelium/moss_block/sand 等可种）。

### Bug2 红石整个失效（P0 实际阻断）—— 已修（根因 = 存储割裂）
- **真因不在引擎逻辑**：`RedstoneEngine` 全程用无维度 `WorldManager.getBlockState(x,y,z)`/`setBlock(x,y,z,state)`，这两个重载只操作 `chunkCache`；而玩家放方块/控制台命令走维度感知版 `setBlock(DimensionType.OVERWORLD,...)`，写入 `dimChunks.get(OVERWORLD)`。**两张独立 map → 红石引擎永远读到 air(0)**。
- 修复：`WorldManager` 让无维度重载统一委托到 `dimChunks.get(OVERWORLD)`（`getChunk(int,int)`→`getChunk(OVERWORLD,...)`；`setBlock(int,...)`/`getBlockState(int,...)`/脏块标记/`FluidEngine.neighborChanged` 全改 OVERWORLD；`preGenerateChunk(int,int)`/`isChunkCached(long)` 同步路由）。`chunkCache`/`dirtyChunks` 退化为死代码（无害）。
- 局限：**下界/末地红石仍只读写主世界**（RedstoneEngine 无维度参数）；`onBlockChanged` 调用点有 `this.currentDim` 可用，nether/end 支持需后续把维度透传进引擎（约 20+ 调用点）。用户实测为主世界，已恢复。

- **WorldManager 双 store 陷阱**：新增任何用无维度 `getBlockState/setBlock` 的子系统前，先确认它要读写的是 `dimChunks.get(OVERWORLD)`。无维度重载现已统一委托，但后续若有人"优化"回 `chunkCache` 会再次引发红石/流体整类失效。

### Bug2 箱子打不开（P0 阻断）—— 已修（真正的根因 = endsWith("_chest") 漏掉普通 chest）
- **两处同一模式 bug**：`BlockStateHelper.isInteractable`(L174) 与 `NetworkHandler.handleBlockInteraction`(L6713) 都用 `name.endsWith("_chest")` 判断箱子。但 `blocks.json` 里普通箱子 name 是 `"chest"`，**不以 `_chest` 结尾** → `isInteractable("chest")` 返回 false → 右键普通箱子根本不进入交互分支（trapped_chest/ender_chest/barrel 因 equals 或 endsWith 仍匹配，唯独最常见的普通 chest 漏掉）。

- 防复发：凡用 `endsWith("_xxx")` 匹配方块名，务必把无前缀的基名（如 `chest`）单独 `equals` 补上。

### Bug3 移动不生成区块、但 tp 可以 —— 已修（对称化错误处理）
- 现象：玩家步行移动时未按位置生成/显示对应区块，但 `/tp` 正常。
- 根因：tp 路径 `sendInitialChunks` 的区块生成有 `try/catch`，而移动路径 `handleMove` 的 IO 线程区块生成**没有 try/catch**。若某区块 `generate()` 抛异常（如结构生成异常），tp 会 catch 继续发其余区块，移动时该异常被 IO 线程静默吞掉 → 该区块永不发送 → 行走出现"空洞/不生成"。
- 修复：`handleMove` 的 IO lambda 加 `try/catch`（与 `sendInitialChunks` 一致），发送前加 `ctx.channel().isActive()` 守卫。

### Bug1 结构高度死板（浮空/埋地房子）—— 已修（jigsaw terrain_adaptation）
- 根因：原代码用**起始区块单一中心列** `topSolidY[colIdx]` 决定整个结构（含跨区块片段）的基准 Y；且所有子片段走 rigid 父相对 Y。某列在坑/峰时整片结构浮空或埋地。
- 修复：`DensityRouterChunkGenerator.placeStructures2` 改用中心 **4×4 列（dx,dz=6..9，共16项）的中位数** surfaceY 作根基准（抗极端值）；`JigsawPlacement.addPieces` 新增 `terrainHeightAt` 参数，非刚性（terrain_matching）子片段按其**局部地形**高度放置；`terrainHeightAt` 落在起始区块外时回退到中位数（避免跨区块片段掉到默认海平线 64）。
- **回归警示（已修）**：采样循环若写 `dx/dz<=10`（5×5=25次）而 `samples` 只分配 16，会在第17次写入抛 `ArrayIndexOutOfBoundsException: Index 16`，恰好卡在 `resolveWorldSpawn` 首次生成区块时导致服务器启动时崩溃。循环上界必须为 `9`（与 16 长度数组匹配）。
- 局限：刚性链（村庄道路）仍跟随起始高度保持平整；跨多区块的大结构边缘起伏仅近似。彻底逐片段地形适配需按任意 (x,z) 求地表高度（当前 topSolidY 仅覆盖起始 16×16）。

### Bug4 容器界面操作玩家背包退出后无效 —— 已修（setSlotItem 同步 window0）
- 根因：在箱子/木桶/工作台/熔炉/漏斗等界面操作玩家背包槽位时，只改了 `data.inventoryIds/Counts`，没把变更同步回 window 0（主背包），关闭界面后客户端回滚。

### 重启后区块随机变海洋 —— 已修（TOCTOU 竞态 + 异步保存丢失）
- 现象：重启服务器后，森林地形中偶尔出现 1~4 个区块变成海洋（水+沙底），边界锐利。
- **根因 1（主因）**：`WorldManager.getChunk()` 用 check-then-act 模式（`store.get(key)==null` → load/generate → `store.put(key,...)`），无任何同步。多线程（IO 线程 + ctx 线程）同时请求同一区块时，两个线程都通过 null 检查，各自独立生成/加载，**后 `put` 的覆盖前者**。若一个生成森林、另一个生成海洋（或加载旧 MCA 数据被新生成覆盖），最终缓存里的是错误的地形。
- **根因 2（放大器）**：`ioExecutor.execute(() -> saveChunkToDisk(...))` 是纯异步的，且**无 ShutdownHook**。服务器关闭时未刷盘的区块全部丢失；下次启动时 MCA 无数据 → 必须重新生成 → 在高并发登录/移动期间触发根因 1 的竞态。
- **修复 A**：`getChunk(DimensionType,int,int)` 和 `preGenerateChunk` 均改为**双重检查锁定（DCL）**：用 `chunkLocks.computeIfAbsent(key, →ReentrantLock)` 按 chunk key 加锁，锁内 double-check 后再 load/generate/put。快速路径（已缓存）无锁。
- **修复 B**：新增 `Runtime.shutdownHook`：`ioExecutor.shutdown() + awaitTermination(10s)`，确保 JVM 退出前所有待保存区块刷盘。日志输出 `[WorldManager] 优雅关闭: 所有待保存区块已刷盘`。
- **教训**：任何 `ConcurrentHashMap` 的 get→条件判断→put 模式（非 computeIfAbsent）在多线程环境下都是 TOCTOU 竞态。chunk 这种"生成代价大且必须唯一"的资源必须加锁。

## 第四轮实测 13 Bug 修复（续：BUG2/BUG7/BUG8 收尾）

### BUG7 生成区块时 TPS 停滞 / 服务器时间冻结 —— 已修（时钟与重型 tick 解耦 + 缓存只读）
- 现象：生成区块时服务器时间与各种停滞，TPS 几乎为 0，区块生成完后恢复。
- **根因**：50ms `WorldScheduler` 单线程既推进游戏时钟（worldAge/dayTime/天气 lerp）又运行全部重型世界 tick（EntityManager/SpawnerSystem/FluidEngine/Redstone/RandomTick/玩家 tickSurvival）。任一 tick 路径调用 `WorldManager.getChunk` 命中慢速路径 → 同步 `generate()` 全地形+特征生成 → 整个任务（含时钟）阻塞 → 时钟停、TPS 显示≈0。
- **修复 A（关键）**：把"游戏时钟节拍"与"重型世界 tick"拆成两个独立 50ms `scheduleAtFixedRate`（`WorldScheduler` 只推进 worldAge/dayTime/天气并每 20 拍广播 0x6F；`WorldTickScheduler` 跑 7 个 tick 子系统）。`scheduleAtFixedRate` 背压会跳过/合并延迟的世界 tick，但时钟永远按 50ms 走 → 服务器时间不再冻结。
- **修复 B**：新增 `WorldManager.getChunkCached(dim,x,z)` / `getBlockStateCached(dim,x,y,z)` —— 未加载区块直接返回 null/0，**绝不触发同步生成**。tick 路径改用它们：`EntityManager.biomeAt`(刷怪群系查询)、`EntityManager.hasSkyAccess`(白天燃烧判定)、`SpawnerSystem.tick`(刷怪笼周围方块读取)。`RandomTickEngine` 本就用 `isChunkCached` 守卫。
- 仍存隐患（非本次范围）：玩家放/破方块走 Netty 线程 `setBlock`→`getChunk` 仍可能同步生成；但玩家可交互时周边区块已被 `handleMove` 异步预加载，且时钟已解耦，不再表现为"时间冻结"。

## BUG7 彻底解决（用户要求"彻底解决"第二轮）

上一轮 BUG7 已把时钟与重型 tick 解耦 + 给几条 tick 路径加了 `getChunkCached`，但**残留隐患**：实体物理(`Entity.isSolidAt/isInFluid`)、Mob 寻路 A*(`Pathfinder`)、`FluidEngine.tick`(processFluid 的 getBlockState+setBlock)、`ExplosionEngine`、`EntityManager.trySpawn*`(findSpawnY/validSpawnGround/isLitNearby 全用 getBlockState)、`tickSurvival` 的火焰/流体写方块、仍全部走 `WorldManager.getBlockState/getChunk/setBlock` 的**同步生成**慢速路径——只要 tick 上读到未加载区块（流体蔓延/火焰扩散/实体越过已加载边界）仍会卡死世界 tick（虽时钟已解耦，但 TPS 仍≈0）。

**本轮彻底修复（线程级开关，一处覆盖全部热路径）**：
- `WorldManager` 新增 `ThreadLocal<Boolean> TICK_THREAD` + `markTickThread()/unmarkTickThread()/isTickThread()`。
- `getChunk(dim,x,z)`：`isTickThread()` 时直接 `return getChunkCached(...)`（绝不进慢速生成路径）；快速路径的 `isFeaturesDone→generate` 也加 `!isTickThread()` 守卫（特征装饰也跳）。
- `getBlockState(dim,...)` 与无维度 `getBlockState(x,y,z)`：`isTickThread()` 时改走 `getBlockStateCached`（未加载返回 air）。
- `setBlock(dim,...)`：`isTickThread()` 且目标区块未加载时直接 `return`（跳过写入，避免触发同步生成）；已加载则正常写。
- `Main.worldTickScheduler` 任务开头 `markTickThread()`，结尾 `finally unmarkTickThread()`——只有 WorldTickScheduler 线程内的所有子系统（Entity/Spawner/EndDragonFight/Fluid/Container/Redstone/RandomTick/tickSurvival）受此开关保护。
- **不受影响**：ioExecutor(handleMove/sendInitialChunks 异步预加载)、Netty 线程(玩家放/破方块、开箱/末地龙蛋构造走 getChunk)、显式重生/传送/末地生成——这些仍走正常 `getChunk` 同步生成（它们本就不在 tick 线程，不会冻结世界 tick）。

**效果**：世界 tick 在任何情况下都不会因"生成新区块/特征装饰"而阻塞 → TPS 不再归零、服务器时间不再停滞。未加载区块在 tick 上表现为 air（物理/寻路宽松），但玩家到达前 `handleMove` 已异步预加载周边区块，正常游玩不受影响。`javac` 通过 EXIT=0。

**验证要点（回归）**：客户端登录/移动/刷怪/流体/火焰/爆炸/实体物理均不触发 tick 线程同步生成；玩家主动放/破方块（Netty 线程）仍正常生成并落盘。若日后要在 tick 上"主动"扩展区块，应改用 ioExecutor 异步预生成再让玩家进入，而非在 tick 内同步 generate。

## 攻击生物/被生物攻击时客户端崩溃（set_entity_motion 解码越界）—— 已修
- 现象（client 20:36:29 断开）：`Failed to decode packet 'clientbound/minecraft:set_entity_motion'`，`readerIndex(9)+length(1) exceeds writerIndex(9)`（包 9 字节，客户端还想多读 1 字节）。
- **根因**：`NetworkHandler.knockback`（包号 `0x63` = `set_entity_motion`/原名 `entity_velocity`）载荷写的是 `writeVelocity` = `VarInt(eid) + 3×Short`(旧 1.20 及以前格式)。但 **1.21.11 该包的 velocity 字段是 `lpVec3`**（协议 `packet_entity_velocity = {entityId: varint, velocity: lpVec3}`），客户端用 lpVec3 解码器读我们的 6 字节 short 载荷会越界。触发链：玩家攻击生物→生物近战反击→`MobEntity:174 nearestPlayer.knockback`→`0x63` 把错误格式的包发给玩家客户端→崩溃。
- **修复**：`knockback` 改为 `pb.writeLpVec3(kx, ky, kz)`（`PacketBuffer.writeLpVec3` 已是 spawn_entity 速度字段的权威编码器，零速写单字节 0、非零写 VarInt+6 字节）。`writeVelocity`(3×Short) 现已无调用方，保留无害。
- **关键协议事实（防复发）**：1.21.11 的 `set_entity_motion`(0x63) 与 `spawn_entity` 的速度字段**都用 lpVec3**，不要用 3×Short（那是 1.20 及更早的 `entity_velocity` 旧格式）。`writeLpVec3` 入参是原始 blocks/tick 速度值（不乘 8000），与旧 `writeVelocity`×8000 不同，切勿混用。
- `javac` 通过 EXIT=0。回归：玩家攻击生物（含生物反击击退）、爆炸击退、末影龙击退均不再崩溃，且击退方向与幅度正确。

## 全面性能优化（内存泄漏 OOM + CPU 90%+）—— 已修

### 问题现象
- 用户 1 人游玩 30 分钟，分配 8GB 内存 OOM（`java.lang.OutOfMemoryError` 在 RMI/nic 线程反复抛出）
- Intel U9 285H (24线程) CPU 持续 90%+
- 连接中断，关掉服务器后 CPU 立即降到 10%、内存恢复正常
- 正常小型服务器 2GB 应足够 5 人游玩

### 根因分析（5 大问题）

**#1 区块永不卸载（OOM 主因，致命）**
- `WorldManager.dimChunks`(ConcurrentHashMap<Dim, Map<Long,Chunk>>) 只增不减
- `DensityRouterChunkGenerator.chunkCache`(ConcurrentHashMap<Long,Chunk>) 是第二份重复缓存，也只增不减
- 每 Chunk ~400-500KB（24 Section × int[4096] = 24×16KB + heightmap/biome/blockEntities 开销）
- 探索 1000+ 区块 → **400-500MB 永久占用**，且随时间只增不减
- `featuresDone`(Set<Long>) 和 `featureLocks`(Map<Long,ReentrantLock>) 同样无限增长
- `FluidEngine.scannedChunks`(Set<Long>) 随区块加载无限增长（每项虽小但累积）

**#2 handleMove 热 I/O（CPU 主因）**
- 每次跨区块边界执行 `System.out.println(...)` —— 同步磁盘 I/O 阻塞 Netty I/O 线程
- 快速移动时高频触发（每 ~1-2 秒一次），每次打印 ~60 字符串

**#3 ioExecutor 线程数过多**
- `Executors.newScheduledThreadPool(4)` —— 4 个线程同时做密集的区块生成（NoiseChunk 插值 + Aquifer + OreVeinifier + SurfaceRules + Carver + Biome + Features）
- U9 285H 虽有 24 线程，但 4 个生成线程 + Netty I/O 线程 + WorldTickScheduler + WorldScheduler 全部争抢 CPU

**#4 Chunk.write() 热路径分配过多**
- 每次 chunk 发送给客户端都调用 `write()`：每个 Section 分配 `new LinkedHashSet<>(4096)`、复杂地形还分配 `new int[4096]` 冗余拷贝、biome 编码分配 `new HashMap<>()` + `new int[64]`
- 视野 12 × 12 = 144 区块，每次跨区块边界可能发送数十个区块

**#5 实体无上限**
- `EntityManager.entities` 无大小限制，刷怪系统持续添加生物
- 生物的 `trackingFor`(per-player Set) 也随之增长
